
# SDD Plan — EnglishVoiceTutor

- **Версия:** 1.0
- **Статус:** Draft

## 1. Цель

Организовать развитие EnglishVoiceTutor по подходу Specification-Driven Development.

Основной процесс:

Specify → Review → Plan → Tasks → Implement → Verify

## 2. Этап 0. Аудит текущего проекта

До реализации новых функций необходимо изучить репозиторий.

### Действия

- Определить структуру модулей и точки входа приложения.
- Найти экраны, ViewModel, репозитории, источники данных и DI.
- Определить используемые STT-, LLM- и TTS-движки.
- Проверить загрузку, хранение и инициализацию моделей.
- Изучить схему локальной базы данных и миграции.
- Проверить существующие тесты и команды сборки.
- Сопоставить текущие функции с требованиями в `specs/`.

### Результат

Для каждого требования определить фактический статус:

- `Existing` — реализовано;
- `Partial` — реализовано частично;
- `Missing` — отсутствует;
- `Needs decision` — требуется продуктовое или техническое решение.

### Критерий завершения

Создана карта соответствия требований текущему коду. Новые задачи реализации не создаются исключительно на основании предположения, что функция отсутствует.

## 3. Этап 1. Спецификации

Проверить и согласовать:
- `voice-conversation.md`;
- `model-management.md`;
- `learning-progress.md`.

Для каждого требования определить:
- входные условия;
- ожидаемое поведение;
- обработку ошибок;
- критерии приёмки;
- необходимые тесты;
- открытые вопросы.

### Критерий завершения

Требования не содержат критичных противоречий и достаточно конкретны для планирования реализации.

## 4. Этап 2. Планирование

Для каждого изменения:
1. определить затрагиваемые модули;
2. изучить текущие архитектурные ограничения;
3. определить зависимости от других задач;
4. оценить риски для пользовательских данных и жизненного цикла приложения;
5. выбрать минимальное решение, удовлетворяющее требованиям.

Архитектурные решения, влияющие на несколько модулей, документируются до реализации.

## 5. Этап 3. Декомпозиция задач

Задачи хранятся в `TASKS.md`.

Каждая задача должна включать:
- уникальный ID;
- ссылку на требования;
- приоритет;
- описание результата;
- критерии приёмки;
- тесты и проверки;
- зависимости, если они есть.

Большие задачи необходимо разделять на небольшие изменения с независимо проверяемым результатом.

## 6. Этап 4. Реализация

Перед началом задачи:
- прочитать связанные требования;
- проверить актуальное состояние кода;
- убедиться, что задача не дублирует существующую функциональность;
- определить необходимые тесты.

Во время реализации:
- не менять несвязанные части приложения без необходимости;
- не обходить ограничения требований ради упрощения реализации;
- обновлять спецификацию при согласованном изменении поведения.

## 7. Этап 5. Верификация

Проверять соответствие требованиям на подходящих уровнях:
- unit-тесты;
- интеграционные тесты;
- UI-тесты;
- ручная проверка на устройстве;
- проверки производительности и ресурсов, если они относятся к требованиям.

Для каждой проверки фиксировать фактический результат.

### Критерий завершения

Все обязательные критерии приёмки выполнены либо оставшиеся ограничения явно задокументированы и согласованы.

## 8. Этап 6. Поддержка спецификаций

После изменения поведения:
- обновить связанные требования;
- проверить связанные задачи и тесты;
- сохранить трассируемость;
- зафиксировать причину изменения.

Реализация и спецификация не должны расходиться.

## 9. Приоритеты

- **P0:** критические проблемы безопасности, целостности данных или основного пользовательского сценария.
- **P1:** важная функциональность и надёжность.
- **P2:** улучшения, оптимизация и функции, требующие дополнительного продуктового решения.

Приоритет назначается после аудита, а не только на основании предположения о состоянии кода.
