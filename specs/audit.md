Документ фиксирует фактическое состояние проекта на момент аудита и карту соответствия требований из `specs/` текущему коду. Статусы требований — по `specs/plan.md`: `Existing`, `Partial`, `Missing`, `Needs decision`.

Пометка **«исправлено при аудите»** означает, что дефект найден и исправлен в этом же изменении. Проверено сборкой и unit-тестами; проверки на устройстве не выполнялись (устройство не подключено, `adb` в окружении нет) — они вынесены в задачи со статусом `Needs Review`.

## 1. EVT-001 — Архитектура

### 1.1. Модули и точка входа

- Один Gradle-модуль `app`. Точка входа — `MainActivity` (Compose, `@AndroidEntryPoint`), `Application` — `EnglishVoiceTutorApp` (`@HiltAndroidApp`).
- `MainActivity` запрашивает `RECORD_AUDIO` и выбирает стартовый экран по наличию `filesDir/model.litertlm`.
- Навигация — `presentation/navigation/AppNavHost.kt`: вкладки `roadmap` / `vocabulary` / `grammar` / `history`, детальные экраны поверх.

### 1.2. Слои и ответственность

| Слой | Пакет | Ответственность |
|---|---|---|
| UI | `presentation/*` | Compose-экраны и `@HiltViewModel`. Голосовой цикл целиком в `ConversationViewModel`. |
| Домен | `domain/*` | Чистые функции и модели: `TutorPrompt`, `ConversationFlow`, `FeedbackParser`, `SrsSchedule`, `TextLayout`, `domain/model/*`. Без Android-зависимостей (кроме моделей состояний). |
| Движки | `data/engine/*` | Интерфейсы `SttEngine` / `TtsEngine` / `LlmEngine` (`Engines.kt`) и реализации. Привязка — только `di/AppModule.kt`. |
| Модели | `data/model/*` | `ModelInstaller` (LLM, HTTP + Range), `ArchiveModelDownloader` (`.tar.bz2` для STT/TTS). |
| Хранилище | `data/local/*`, `data/repository/*` | Room v3 (`conversations`, `messages`, `vocab_progress`, `topic_progress`), SharedPreferences (`ModelPreferences`, `VoicePreferences`). Репозитории склеивают Room и статический курс. |
| Курс | `data/curriculum/*`, `assets/curriculum/*.json` | Статический контент A1–C1, парсинг `org.json`, кеш в памяти. |

### 1.3. Ключевые зависимости

- LLM: `com.google.ai.edge.litertlm:litertlm-android:0.17.0` (Gemma 4 E2B/E4B), GPU → откат на CPU.
- STT/TTS: `com.github.k2-fsa:sherpa-onnx:v1.13.8` (Parakeet 0.6B int8; Piper LibriTTS-R medium).
- Распаковка: `commons-compress 1.27.1`.
- Hilt 2.60.1, Room 2.8.4, Compose BOM 2026.06.00, Kotlin 2.3.0, AGP 9.2.1, Coroutines 1.11.0.
- Подключены, но не используются активным кодом: `vosk-android` (fallback `VoskSttEngine`), `work-runtime-ktx` (WorkManager нигде не используется).

### 1.4. Потоки данных

**Голосовой ход:** тап по микрофону → `SherpaOnnxSttEngine.startRecording()` (при первом вызове — загрузка ~500 МБ и загрузка модели в память) → `AudioRecord` 16 кГц в отдельном потоке → второй тап → `stopRecording()` декодирует всю фразу → `ConversationRepository.getContextForResume()` (первые 4 + последние до 50 сообщений в пределах бюджета, `domain/ConversationContext`) → запись реплики в Room → `LiteRtLlmEngine.generateReply()` (один поток `litert-llm`, `Mutex`) → запись ответа в Room → `SherpaOnnxTtsEngine.speak()` (по предложениям, `AudioTrack`) → `Idle`.

**Модели:** LLM — по явной команде пользователя на экране настройки/настроек; STT и TTS — лениво при первом использовании. Все файлы — в `filesDir`.

**Сеть:** только загрузка моделей (HuggingFace, GitHub Releases, произвольная ссылка пользователя). Диалог, распознавание, синтез и разбор ошибок — на устройстве. Пользовательские данные во внешние сервисы не отправляются (проверено по коду: единственные HTTP-клиенты — `ModelInstaller` и `ArchiveModelDownloader`, тело запроса не передаётся).

### 1.5. Спорные и неочевидные решения

1. **ViewModel зависит от конкретных классов.** `ConversationViewModel` получает `SherpaOnnxSttEngine` (ради `downloadState`) и `ModelInstaller` (конкретный класс с `Context`) — поэтому голосовой цикл нельзя проверить JVM-тестом с подменами (VC-010). Это главное препятствие для EVT-105.
2. **Голосовой цикл — в ViewModel**, а не в отдельном доменном классе. Состояния (`VoiceUiState`) и переходы не вынесены в проверяемую машину состояний.
3. **WorkManager подключён, но не используется** — загрузки идут в `viewModelScope` и прерываются уходом с экрана.
4. **`vosk-android` в APK ради неактивного fallback** — добавляет нативные библиотеки без выравнивания 16 КБ (lint `Aligned16KB`).
5. **Ленивая загрузка STT (~500 МБ) при первом тапе по микрофону** — пользователь узнаёт о ней только в момент разговора.
6. **`LlmEngine.summarize`** объявлен и реализован, но нигде не вызывается (упрощение MVP, см. README).

## 6. Журнал исправлений

Подробности «было → стало» по задачам из `TASKS.md`. Статус и оставшиеся проверки — в самих задачах.

### EVT-102

- «Завершить» во время генерации не отменял ход — ответ записывался и озвучивался. Теперь операция — один `Job` (`ConversationViewModel.activeJob`), `endConversation()` его отменяет.
- `CancellationException` перехватывался общим `catch (Exception)` и показывался как ошибка — теперь пробрасывается.
- Двойной тап во время первой загрузки STT запускал две загрузки (`SherpaOnnxSttEngine` — `Mutex`, VM — состояние `Preparing` ставится до suspend).
- Озвучка не реагировала на отмену корутины — проверка `isActive` в цикле синтеза.

### EVT-103

- Сбой декодера в `stopRecording()` не перехватывался — падение процесса. Теперь → `VoiceUiState.Error`.
- Пустой результат молча возвращал в `Idle` — теперь сообщение «Не удалось распознать речь…» с возможностью повторить.
- Отсутствие модели STT выглядело как пустая речь — теперь исключение.
- Неинициализированный `AudioRecord` давал пустую запись — теперь понятная ошибка.
- Ошибка TTS: текст реплики уже сохранён, баннер `TtsStatusBanner` показывает причину — подтверждено чтением кода.

### EVT-204

- LLM качалась прямо в `model.litertlm`, и `MainActivity` считала приложение готовым по наличию файла — недокачанная модель выглядела установленной.
- При смене модели рабочая модель удалялась до начала загрузки новой.
- Докачка могла склеить байты двух разных моделей (сравнивался id установленной модели, а не той, что лежит в файле).
- Распаковка STT/TTS шла прямо в итоговый каталог — прерванная распаковка могла пройти проверку «файлы на месте».

Теперь: `model.pending.litertlm` + id/URL в `ModelPreferences`, активация переименованием после успешной инициализации; архивы — staging-каталог `.unpack-*` и перенос переименованием.

- **Регрессия, найдена на устройстве 2026-10-20 (P0):** движок поднимался с `model.litertlm.part`, а LiteRT-LM определяет формат по расширению — полностью скачанная модель (≈ 2,67 ГБ по `netstats`) отвергалась с «Unsupported or unknown file format» и удалялась. Временный файл переименован в `model.pending.litertlm`, остатки под старым именем удаляются; при сбое инициализации в лог пишутся размер и сигнатура файла. Проверено повторной загрузкой: файл 2 588 147 712 байт поднялся на GPU и стал `model.litertlm`.

### EVT-502

- При входе в диалог LLM инициализировался дважды: прогрев из `init` `ConversationViewModel` и первый ход одновременно звали `ModelInstaller.ensureInitialized()`, второй вызов закрывал готовый движок. Теперь — `initMutex` с повторной проверкой. Проверено на устройстве.

### EVT-110

- Отбор контекста LLM вынесен в чистую функцию `domain/ConversationContext.select` (тест `ConversationContextTest`): 4 первых + до 50 последних сообщений в пределах 10 000 символов вместо 4 + 20. Неиспользуемые запросы `getFirstMessages` / `getRecentMessages` / `countMessages` удалены из DAO.
